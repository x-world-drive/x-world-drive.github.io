TL;DR：X-World 1.5 每次同步生成并回传七路相机画面，单帧合计约 230 万像素，约为单视角 720p 的 2.5 倍。在 4 张 GPU 上，在线交互推理达到 12 FPS（训练数据的原生帧率上限）。p50 操控到画面延迟（不含网络）为 426 ms，相比未优化版本延迟降低了 73.7%。在同类交互式世界模型中达到目前已知的 SOTA 推理水平。

X-World 1.5（下文简称 X-World）是小鹏面向智驾仿真的世界模型，根据历史画面、车辆动作和场景条件持续生成七路相机视频。模型在 latent 空间按 chunk 自回归生成，用滚动 KV cache 复用历史特征。DiT 的 temporal attention 处理每个视角的时间序列，cross-view attention 在同一时刻的不同相机之间交换信息。后者用相机位置编码 PatchCaPE 增强视角间的空间一致性。物体、车道线和路面标线由结构化条件分支输入，红绿灯单独处理。

X-World 可以持续接收智驾模型输出的动作，推演不同驾驶决策下的环境变化，用于大规模闭环评估和在线强化学习。我们在此基础上加入了实时驾驶模式：开发者用方向盘和踏板控制车辆，车辆运动学模型把转向、油门和刹车转换为自车轨迹，再输入世界模型。人工驾驶更容易做出急转、急刹这类偏离训练分布的操作，也能直接看出世界模型能否及时、连续地响应。

离线闭环仿真和一般的视频生成更关注吞吐。像多任务并发、批处理和我们之前提出的 X-Cache 都能提高整体效率。然而，和闭环仿真有所不同的是，实时驾驶还要求每次反馈足够快：在相同模型、画质和硬件下，既要维持 12 FPS，又要尽快把新的转向和刹车反映到画面上。帧率高不等于操控延迟低，偶发的尾延迟也会直接表现为卡顿。

我们最初只打算回传主视角，以减少 VAE 解码和网络传输的开销。后来改为完整回传七路画面。因为测试者在转弯、并线时可以同时观察前方和侧后方，检查各视角是否连贯一致。七路画面合计约 230 万像素，约为单视角 720p（1280 × 720）的 2.5 倍。一次操作上传后，DiT 对七路 latent 多步去噪，VAE 把 latent 解码为图像，七路画面分别编码、经网络回传，再由浏览器解码显示（图 1）。七路画面必须同步，任何一路变慢都会推迟整组画面。

注：

  • 下文的所有测试都是回传完整的七路画面，帧率则按客户端在连续生成阶段（跳过最初几轮预热）收到的帧来计算。
  • 首帧接收延迟的定义是：从发出操作到收到对应的第一帧的延迟，不包含网络传输和浏览器解码的时间。不过我们也对网络传输的部分做了一些优化，详见第六节。

一、用 Breakable CUDA Graph 降低 kernel launch 开销

最初的 DiT trace 里，许多 kernel 只执行几微秒，相邻 kernel 之间却有明显空隙。一个 8 帧 chunk 要调用 97265 次 cudaLaunchKernel，trace 中 GPU busy 只有 34%。GPU 算完一个 kernel，常常要等 CPU 提交下一个（图 2a）。

CUDA Graph 可以省掉这些提交，但结构化条件和红绿灯的 token 数随场景变化。graph 预热的 34 个 chunk 里，结构化条件出现了 21 种长度。按长度分别 capture 会增加预热时间和显存，graph 的复用率也低。我们也试过把车道线 token padding 到固定长度，然而输出没能保持逐字节一致。

我们采用了 SGLang 提出的 Breakable CUDA Graph（BCG），把变长条件分支留在 graph 外 eager 执行。capture 到这些分支时，先结束当前 graph segment，执行这部分计算，再继续 capture 后面的操作，这个中断位置就是 break。replay 时按同样顺序交替执行 graph segment 和 break，各段 graph 共用一个 memory pool。

Token 数变化并不改变这些分支的输出形状。分辨率和 chunk 长度固定后，视频 query 的数量固定，attention 输出与 query 同形状，可以交给后面的 graph。输出地址也要固定：capture 时后一段 graph 记录了 break 输出缓冲区的地址，replay 时 break 把新结果写回这块缓冲区，再执行后一段 graph（图 3）。这块缓冲区和 graph 一起保留，replay 不会读到已释放的地址。

基于 torch.compile 的 Piecewise CUDA Graph（PCG）当然也能分段执行，但我们的部分 kernel 需要额外的编译适配，通信顺序也要重新验证。SGLang 的博客记录了类似问题，并在 prefill 测试中还观察到 PCG 额外的 guard check 和 dispatch 开销。因此我们选择 BCG，沿用现有的 kernel 和通信实现。

X-World 每层有 4 个 break：前视、侧视和后视三个相机组的红绿灯 attention 各一个，结构化条件 attention 一个。四步去噪共经过 480 个 break，切出 481 个 graph segment；KV finalize 再执行 121 个，一个 chunk 合计 602 次 graph launch。

break 内的 kernel 仍由 CPU 逐个提交。一个 chunk 剩下的 20819 次 cudaLaunchKernel，约 98% 来自这些 break。看得到红绿灯的相机组每层约 116 个 kernel，结构化条件 attention 约 29 个，没有红绿灯的相机组直接输出全零，只需 1 个。在开启 BCG 后，GPU busy 从 34% 升到 92.8%。连续生成时单个 chunk 的 DiT 耗时 p50 从 2231 ms 降到 1080 ms，首帧接收延迟从 5311 ms 降至 2622 ms。帧率从 3.61 FPS 提高到 7.42 FPS。

二、用 UCP 缩短 DiT 计算时间

BCG 减少了 CPU 提交带来的等待，但每轮去噪的计算量没有变。我们用 Ulysses Context Parallelism（UCP）把一次 DiT 推理分到三张 GPU 上，第四张 GPU 负责 VAE 编解码。

UCP 按相机切分七路的空间 token。前视、侧视和后视的 token 数不同，各卡分到的 token 数也可以不同。self-attention 和 cross-view attention 各自按需要的布局交换数据，文本和场景条件分支直接处理本卡的 query。

为了在 UCP 下继续使用 BCG，我们提前分配收发缓冲区，固定各 rank 的通信顺序，在当前 CUDA stream 上直接调用 NCCL。通信和计算一起 capture、一起 replay，变长条件仍留在 break 中。改为三卡后，帧率从 7.42 FPS 提高到 11.29 FPS，p50 首帧接收延迟从 2622 ms 降到 1622 ms。

多卡配置确定后，我们继续优化单卡 kernel。为了不让算子融合和调度变化影响浮点结果，我们固定场景、动作序列和采样噪声，以三卡 eager 连续生成的七路图像和 latent 为基准，后续每项优化的输出都会和此基准进行比较，确保推理优化不会降低最终生成质量。

三、kernel 层优化

开启 BCG 和 UCP 后，逐元素计算和数据复制仍占每层 kernel 总耗时的约 61%。这些操作常常接连读写同一份数据：前一个 kernel 刚把中间结果写回显存，后一个 kernel 又把它读出来。我们把相邻操作融合，让输出直接采用下游需要的布局，省掉中间读写和单独的 launch。

首先，最常见的融合对象是 QK 的 RMSNorm 和 RoPE。我们把两者合成一个 Triton kernel，在寄存器里完成归一化和旋转后直接写回。基线 RoPE 在 FP64 下计算旋转再转回 BF16，直接改用 FP32 会改变部分元素的值。融合 kernel 保留原有的 reduction 顺序和中间舍入，先用 FP32 计算；误差上界内的区间都舍入到同一个 BF16 值时直接写出，落在舍入边界上的元素才在同一个 kernel 内回退到 FP64 重算。融合后，单次 Q/K 归一化加旋转从 135.6 µs 降到 17.5 µs。

每层还要反复执行带调制和门控的 adaLN 和残差连接。我们把各层的 adaLN 参数提到层循环之前统一生成，再把归一化、调制、门控残差和行重排合进一次 kernel launch，在寄存器内保留原有的 BF16 舍入和 reduction 顺序，单次耗时从 16.9 µs 降到 6.3 µs。

Q、K、V 投影共享输入，拼接权重后一次 GEMM 就能算完，但拆出的三个结果是 strided view。如果再各做一次连续化复制，GEMM 省下的时间就被显存 copy 抵消了，所以后面的归一化、RoPE 和通信都直接读这些 view。UCP 的通信原来要先打包、再调用 NCCL、接收后再调整布局。我们把布局转换合进跨卡写入，直接写到接收方需要的位置。单独合并 QKV 投影会让单层耗时从 2435 µs 增加到 2522 µs，配合跨卡写入后降到 2167 µs（图 5）

原本的 PatchCaPE 按相机组逐个做几何投影和横纵坐标的二维 RoPE，最后再拼接，拆成了大量小 kernel 和中间 tensor。我们把整条序列的变换合成一个 Triton kernel，直接按 attention 需要的布局写出，单个 KV 变换从 191.0 µs 降到 4.4 µs。

结构化条件 attention 中拆开的指数、行求和与归一化合成一个 masked softmax kernel，耗时从 61.1 µs 降到 9.5 µs。红绿灯 attention 原本按四组帧条件分别调用 masked SDPA，现在合为一次 launch。为了让这条分支进入 graph，红绿灯数量补齐到 16 个，K、V 投影和 attention 仍只计算有效红绿灯。结构化条件分支的 Q 投影、输出投影和残差也移进了 graph，break 里只剩变长 token 上的 attention。图 4 对比了主要融合算子与 PyTorch 原始版本的耗时。

在三卡 BCG + UCP 上逐项叠加这些优化（图 5），DiT 单层平均耗时从 3075 µs 降到 1007 µs（减少 67.3%），单层执行的 kernel 数从 510 降到 55，每张卡每个 chunk 由 CPU 直接发起的 cudaLaunchKernel 降到约 510 次。帧率从 11.29 FPS 提高到 11.78 FPS，p50 首帧接收延迟从 1622 ms 降到 1430 ms。

四、降低操控延迟

kernel 优化之后，每轮返回 8 帧的版本 p50 首帧接收延迟仍有 1430 ms。这段时间并不全花在计算上：每轮在采样开始时读入动作，生成过程中新到的转向或刹车，要等下一轮才能进入模型。要让操作及时生效，就得缩短动作更新的间隔。

从 8 帧到 2 帧反馈

X-World 的 DiT 每次对两个 latent（L₁、L₂）联合执行四步去噪。VAE 在时间维度上压缩 4 倍，L₁ 对应第 1～4 帧，L₂ 对应第 5～8 帧，一个 chunk 共覆盖 8 帧。chunk 内的 L₁ 和 L₂ 双向交互，chunk 之间用历史 KV cache 传递上下文。

闭环仿真每轮只返回一帧：驾驶模型拿到新画面后重新规划轨迹，X-World 从同一份初始噪声出发，按最新轨迹对当前 chunk 重新去噪，再解码出所需的那一帧。动作可以逐帧更新，但连续输出 8 帧需要对整个 chunk 去噪 8 轮。实时驾驶最初直接返回单轮采样的全部 8 帧，整个 chunk 只去噪一次，但 8 帧共用同一组动作，在 12 FPS 下间隔约 667 ms。把 chunk 缩成单个 latent 也不可行：模型按两个 latent 一个 chunk 训练，只用一个 latent 时，画面会随生成逐渐变模糊。

因此我们保留双 latent 和四步去噪，在同一个 chunk 内分多轮读入新动作（图 6）。四帧反馈每个 chunk 采样两轮，第 1 轮返回 L₁，第 2 轮返回 L₂，动作更新间隔缩到 333 ms。X-World 的速度、曲率等动作条件按帧输入，同一个 latent 的 4 帧可以使用不同时刻的动作。两帧反馈因此每 2 帧（约 167 ms）读入一次操作，一个 chunk 分 4 轮采样：第 1、2 轮分别返回 L₁ 的第 1～2 帧和第 3～4 帧，第 3、4 轮分别返回 L₂ 的第 5～6 帧和第 7～8 帧，只有第 4 轮写入历史 KV cache。

已经发给客户端的画面无法撤回，而 L₁ 和 L₂ 在 chunk 内双向交互，更新后续帧的动作也会改变前面帧的生成结果。为保持各轮画面前后衔接，两帧反馈采用与逐帧闭环仿真一致的全 chunk 联合重采样：每轮都从同一份初始噪声出发，在相同噪声步 t 下联合去噪 L₁ 和 L₂，已返回的帧保留当时的动作，其余帧使用最新动作；VAE 对同一个 latent 的两次解码共用同一份历史 cache，待该 latent 的后两帧确定后再更新。第 3、4 轮也不能直接复用第 2 轮去噪好的 L₁（t = 0）：模型训练时并没见过“L₁ 已经干净、L₂ 仍带噪声”的输入。经测试，这样做会让三路相机 PSNR 下降 0.20 dB～0.34 dB、物体闪烁明显增加；而且 L₁ 在每层仍参与 bidirectional attention，固定它并不能节省 DiT 计算量。采用全 chunk 联合重采样后，4 段实车场景回放的输出与逐帧闭环仿真逐字节一致；实时驾驶时 PSNR 相差在 0.08 dB 以内，车辆和行人的异常闪烁分别只比逐帧闭环多约 3% 和 6%，集中在每个 chunk 的第 3 帧。

反馈间隔还可以按场景需求调整：例如强化学习时需要每帧一次反馈（每个 chunk 采样 8 轮），才能真实反映实车的逐帧闭环决策；实时驾驶则采用两帧反馈，将每个 chunk 的采样轮数控制在 4 轮。

让两帧反馈也能维持 12 FPS

两帧反馈下，每个 chunk 的 DiT 去噪、VAE 解码和视频编码次数都是 8 帧返回模式的 4 倍。这也是为什么我们没有采用延迟更低，但是算力要求更高的单帧反馈。要在 12 FPS 下不积压请求，单轮两帧输出平均必须在 167 ms 内完成，否则新操作又要排在旧请求后面等待。为此，我们先去掉 chunk 内的重复计算：每个 chunk 只在结束时执行一次 KV finalize，即两个 latent 都确定后再做一次 forward 写入历史 KV cache；VAE 也只解码本轮需要的画面，每个 latent 的第一轮只解前两帧，第二轮解出完整四帧并返回后两帧。

除减少单轮计算外，我们还让相邻两轮的生成和输出重叠执行。DiT 读取的是去噪完成的 latent 写入的历史 KV，不需要解码后的图像，因此当前 DiT 提交后即可启动下一轮，与当前轮的 VAE 解码、视频编码和回传并行执行。chunk 末尾的 KV finalize 也与 VAE 解码并行：二者读取同一份 latent，而 KV finalize 不会改写它（图 7）。

要让图 7（b）的重叠真正跑起来，主机线程和 CUDA stream 上还不能有隐藏的阻塞。排查后我们去掉了几处多余的同步等待：DiT 导出 latent 前原本调用 torch.cuda.synchronize() 阻塞主机线程，改为记录 CUDA event 交给下游 stream 等待；跨进程发布帧缓冲区的等待原本排在默认 stream 上、要等当前轮的计算结束，现在移到独立 stream；条件上传改为复用 pinned memory 的异步复制，用于确认计算完成的 tensor 也直接在 GPU 上生成，输入准备不再被同步复制卡住。

当下一轮请求可以提前准备并与本轮输出重叠时，请求的提交时机也会影响延迟。动作在提交时就已固定，如果过早提交，DiT 还在跑上一轮时新到的操作就只能再等一轮。因此我们只提前准备下一轮请求，等 DiT 快要空闲时才读取最新操作并提交；去掉这一机制后，帧率会降到 11.82 FPS，p50 首帧接收延迟也会增加 7 ms。

在输出链路末端，VAE 解出的画面按帧编码发送。CPU 使用 SVT-AV1 的实时低延迟模式，以恒定码率编码并关闭 lookahead；七路并行编码，码率按像素数分配，同一时刻的七路画面编码完成后一起发出，浏览器用 WebCodecs 解码。连续生成阶段，每次两帧的七路编码耗时中位数为 28.5 ms。

最终，这一系列改动让 DiT 去噪、状态提交和视频编码都控制在 167 ms 预算之内，两帧反馈的 p50 首帧接收延迟也从 1430 ms 降到 1275 ms。但每 8 帧要做 4 次七路解码，单卡 VAE 解码成为新的瓶颈，帧率暂时落到 5.58 FPS，第五节将单独解决这一问题。

避免持续交互中的停顿

除单轮推理的平均开销外，长时间连续交互中还会偶发数百毫秒的停顿。给 Python GC 加上计时后发现，会话期间单次 GC 最长暂停 674 ms；任何一个 DiT rank 停下来，其他 rank 都会在通信处等待。

GC 会反复遍历模型加载和 graph 预热后留下的大量常驻对象。我们在预热结束、还没有会话时手动触发一次 GC，再调用 gc.freeze()，之后的 GC 跳过这些对象，新会话创建的对象照常回收。修改后单次 GC 最长暂停 18.7 ms。各统计 148 次稳态请求，网关侧请求耗时的 p99 从 863 ms 降到 410 ms，最大值从 993 ms 降到 520 ms（图 8）。

五、七路 VAE 解码优化

两帧反馈下，负责 VAE 的 GPU 平均每 167 ms 要处理完一次七路两帧请求。优化前，一次请求要占用 GPU 345.2 ms，帧率因此降到 5.58 FPS。我们保留三卡 DiT、单卡 VAE 的分工，直接缩短七路解码的耗时。

原始解码在卷积前后频繁切换 tensor 布局，还要分配和复制中间结果，七路高分辨率输出把这些开销放大了。我们让卷积之间的 tensor 保持 channels-last，权重只在初始化时转换一次。卷积前的 RMSNorm、SiLU、历史特征拼接和 padding 融合执行，直接生成下一层卷积的输入；卷积后的 bias 和残差相加也做了融合。

VAE 在时间维度上是因果的，第一次反馈只返回前两帧，可以省掉后两帧的解码。缩短时间维或改用 channels-last 可能触发不同的 cuDNN 卷积算法，改变浮点累加顺序。我们逐层挑选能复现完整解码结果的 cuDNN plan，要求像素取整前的输出和 decoder cache 都一致；没有匹配 plan 的层保留完整形状计算，再截取前两帧。

七路相机各自维护解码状态，彼此没有数据依赖。我们为每路分别 capture 两帧解码、四帧解码、末帧重编码和解码状态准备的 CUDA Graph，在独立的 CUDA stream 上 replay。同一视角内部仍按时间顺序执行。最后，我们把部分卷积换成了更快的卷积 kernel。

叠加这些改动后（图 9），每次请求的 VAE GPU 时间从 345.2 ms 降到 141.8 ms，kernel 数从 8241 降到 2241，低于 167 ms 的要求。帧率回到 12.01 FPS，p50 首帧接收延迟为 457 ms。

六、其他杂项与网络传输优化

帧率优化回 12 FPS 后，我们在真人试驾中继续排查实际场景中的操控延迟。GPU 上的 DiT 和 VAE 已经压下去了，剩下的延迟散落在去噪前后的 CPU 处理和请求提交时机上。

去噪前最耗时的是红绿灯条件准备：原先在 CPU 上把红绿灯画成全分辨率图像，传到 GPU 再用自适应最大 pooling 缩到 latent 网格。模型只用 pooling 后的 0/1 mask，而红绿灯包围盒外全是 0，我们改成在 CPU 上只遍历包围盒覆盖的网格窗口，直接生成并上传 latent 分辨率的 uint8 mask，去噪前准备时间 p50 降到 11.5 ms。配合微调前面提到的状态提交提前量，服务端耗时 p50 从 392 ms 降到 380 ms。

接着我们又清掉了三处服务侧开销：结构化条件只传整数类别 ID 由 DiT 直接查表；HUD 几何计算挪到去噪请求发出之后；VAE 解出的画面直接转发网关，省掉一次内存复制。服务端耗时 p50 进一步降到 345 ms，p99 从 410 ms 降到 401 ms，p50 首帧接收延迟从 457 ms 降到 426 ms。

实际交互通过浏览器跨公网连接，客户端同时接收七路 AV1 视频流。在往返时延 158 ms 的链路上，稳态下从发出操作到收齐画面的延迟 p50 为 613 ms，p99 为 707 ms；浏览器内从按键到画面上屏的 p50 为 614 ms，视频帧到达后约 20 ms 内完成解码和绘制。

我们在驾驶中还发现，每次刚连上页面、第一次按键后的前 3 秒画面都会明显卡顿：单帧传输耗时的 p50 高达 669 ms，最高 1576 ms，浏览器每秒只能收到 2～10 帧，积压的画面随后才成批涌入（图 10）。原因是新建 TCP 连接还在慢启动阶段，发送速率没拉起来，服务端按 12 FPS 生成的七路视频只能堵在发送端。

为此我们在开放操作前先预热连接：页面连上后，服务端先按视频码率下发 4 秒随机数据，浏览器逐块确认，把 TCP 发送窗口撑开后再接收操作。加上预热后，前 3 秒单帧传输耗时的 p50 降到 91 ms，第一次操作到收到首帧从 610 ms 降到 433 ms，前 3 秒操作到收齐画面的 p50 从 1389 ms 降到 629 ms。

下一步：推理全流程 RSI

回顾前面的优化，每一步其实都在重复同一个过程：读 trace 和运行日志，定位 kernel launch、算子融合、通信、调度上的瓶颈，提出假设，修改实现，再验证性能和生成质量。一个方向失败就回退，多个方向分别尝试。这个过程可以看成不断展开和剪枝的搜索。

这类任务适合构建一个 RSI 来进行全自动优化。英伟达的 KDA 等工作已经表明，结合正确性检查、benchmark 和 profiler，Agent 可以持续生成、测试和改进 kernel 代码，部分结果达到或超过人类工程师的水平。事实上，在我们的工作中，部分 bug 就是完全依赖 Agent 自身找到的。例如， Python GC 的问题就是它阅读不同层级的日志、逐项排查后定位并解决的。目前，也有一些 RSI 系统尝试自动优化整个推理框架（不仅仅是某一个点），并声称在特定测试中超过主流开源框架。不过我们对这些结果在实际场景中的效果仍持怀疑态度。

Agent 会忠实地优化我们定义的目标。然而，benchmark 或 verifier 有漏洞时，它也可能会 cherry-picking，得到看似漂亮、实际没有意义的结果。OpenAI 在 Jalapeño 芯片开发中的实践值得参考。工程师先把系统设计成边界清晰、行为可预测、结果容易验证的 programming target，再让 AI 在其中反复尝试不同的调度和实现。

我们希望在推理优化上采用类似的思路：逐步把 trace、运行日志、基准测试和正确性测试接入 Agent 的工作环境。同时，考虑到模型的上下文窗口终究有限，我们也希望能够将每轮探索中真正有价值的信息持续沉淀为可复用的长期记忆，让 Agent 在后续迭代中能够利用过去的经验，而不是不断从头摸索。最终，让它在明确的目标和约束下，形成一个能够不断积累经验、持续自我改进的优化闭环。每轮可以只提升 1% 或 2%，但这 1% 的提升必须真实有效。

在这过程中，人类工程师的“品味”仍然非常重要。什么问题值得优化、应该开放怎样的搜索空间、哪些指标值得相信，以及什么时候应该怀疑一个过于理想的结果，这些并不是简单增加搜索次数就能解决的。当然，这也不意味着这些判断永远只能由人类完成。随着 Agent 能力和工具链的不断完善，我们有理由相信，它能够逐步承担越来越多原本依赖工程师经验和直觉的工作。因此，比起依赖少数“优化仙人”的个人经验，我们更希望将这些经验和判断逐步沉淀到可复用、可验证、可持续改进的 Agent 工作流中。真正值得持续投入的，不只是某一次具体的优化，而是优化流程本身的迭代。只有不断提升整个系统发现问题、提出假设、执行实验和验证结果的能力，才能让 infra 的迭代速度真正跟上模型的迭代速度。
